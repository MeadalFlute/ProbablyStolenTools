# 完整 int[] 载荷优化

## 背景与选择

17:50 实机日志证明上一轮 owner 二次修复已把第二次写回降至 14-16 ms。主要成本转到捕获 walk、首次完整 write 和 Census，不能再从二次修复挤出同量收益。

先尝试过访问器内的单对象查找缓存，缓存的是已保留对象及存储描述，不是字段值。首轮原生隔离夹具（5 个样本）捕获 46.55 -> 46.07 ms、普查 34.03 -> 35.90 ms、写回 26.10 -> 25.92 ms，收益不足以证明值得部署。该原型、开关及专用测试已撤除，没有独立发布或改变玩家设置。

本轮改为现有字段块接口下的完整 int[] 载荷。这是对既有物理存储的无损强类型保存，不是逻辑字典重建，也不是原版 SaveGame/LoadGame。

## 范围与不变量

- 新类 SnapshotIntArrayBlock 只保存精确非空 int[] 的独立完整 Clone；保留原数组对象，恢复用 Array.Copy，不替换目标数组，不缩小容量，不跳过未用桶或槽。
- 工厂使用 GetType() == typeof(int[])，不使用 is int[]；回归测试验证 uint[] 等非目标类型不会误入 CLR 特殊数组兼容路径。空数组、其他元素类型、带筛选字段的显式根继续原槽位路径。
- 原有数组维度、下界、长度规则不变。先完整描述并检查剩余槽/字节预算，再创建载荷；逻辑预算仍为每元素 1 槽 / 8 字节，不能因为物理 int 为 4 字节就放宽预算。
- 不改变图的全部对象、数组、字符串身份、发现顺序、来源路径及引用。int[] 本来没有引用槽，块不会引入新的遍历边；字典 entries/buckets/version/free-list、缓存视图及活动枚举器保持原恢复规则。
- 不调用业务 setter，不用 unsafe，不生成新写入委托，不改游戏程序集、存档、其他 Mod 或加载器。
- 仍先写全部普通标量和块标量，再写全部普通引用和块引用。int 数组复制属于块标量阶段；自身没有引用写入。
- 完整逐元素比较，不受诊断上限影响；报告原来的 System.Int32[][index] 槽名。VisitCapturedSlots 仍展开所有捕获槽，独立语义 Shadow 与所有权审计不丢失数组存储。
- 整数组是一个变化 owner，owner 修复计划按完整长度计槽；超过修复槽上限回退原全图路径。首次完整恢复、预检、最终完整校验、最终差异回退和视觉/几何顺序均不改变。
- Census 不创建块，不 Clone，不保存值令牌，仍通过既有 ProbeValue 读所有字段。本轮不优化普查代码。

## 设置与日志

新增 `Snapshot.IntArrayBlocks=true`，启动 Session 输出 intArrayBlocks 开关，CAPTURE 输出：

```text
backend=hybrid-exact-tag tagBlocks=... intArrayBlocks=... intArraySlots=...
```

tagBlocks 扣除 int 数组块，仍仅计精确标签载荷；intArraySlots 是原逻辑元素槽数，不是减少的字节数。没有增加每帧、逐元素或逐块日志。

关闭开关并重启，新节点使用普通逐元素令牌。已保留节点始终由自己的载荷解释，不依赖后续捕获工厂。现有五参数 ManagedStateAccess 构造器保留不启用 int 块的行为，六参数最后一项用于本次显式实验及原生对照；游戏统一访问器工厂读取配置。部署不预改玩家 settings。

## 隔离性能测量

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run -c Release --project tests/ReleaseCompatibility/ReleaseCompatibility.csproj -- `
  "E:\SteamLibrary\steamapps\common\Probably Stolen" `
  src/ProbablyStolenTools/bin/Release/Mono/ProbablyStolenTools.dll release/manifest.xml --benchmark-int-arrays
```

用真实程序集未初始化业务对象，在 .NET 6 中运行，不启动 Unity。两种模式均启用相同标签块、直接字段写入及全部校验，唯一载荷差异为是否启用 int[] 块。每轮先 GC，三轮预热、交替顺序九轮取中位数；首次探索用的五轮默认分层编译结果不作为正式收益估计。

夹具为 1024 字典 / 16384 标签（含子类/别名），共 53253 对象、349232 逻辑槽、2793856 逻辑字节。启用 int 块后覆盖 1024 个数组 / 37888 槽；每轮完整校验恢复结果。

两次独立运行，表中均为普通 int 槽位 / int 块：

| 指标 | 运行 1 | 运行 2 |
| --- | ---: | ---: |
| 捕获 ms | 45.60 / 28.43 | 40.07 / 28.56 |
| 完整校验 ms | 10.20 / 8.38 | 9.46 / 7.99 |
| 完整写回 ms | 31.66 / 29.24 | 30.30 / 29.54 |
| 捕获分配 B | 48818200 / 48910264 | 48820000 / 48910264 |
| 写回分配 B | 6062080 / 6062080 | 6062080 / 6062080 |
| Census ms（代码未变） | 35.67 / 22.14 | 34.08 / 21.53 |
| Census 分配 B | 23495184 / 23495184 | 23495184 / 23495184 |

捕获在此夹具改善约 29-38%，写回约 3-8%，不等于 Unity 收益。分配量没有改善，实际略增约 0.2%；完整 Clone、块对象及 List 容量阶梯会影响结果，不宣称降低实际内存。Census 在目标快照仍保留、且刚完成对应捕获/校验后运行，并非独立隔离的普查 A/B，可能受存活载荷、GC/缓存状态等影响；代码没有减少任何普查工作，不能把表中 Census 差值算作已实现优化。

基准不含 Unity 视觉、几何、真实完整存档、全局帧调度或第三方 Mod。暂不承诺整次捕获/恢复达到此比例，也不据此扩大到引用或结构体数组。

## 实机停止边界

本轮改变真实快照载荷，部署后停止，等待用户方便时：

1. 重启游戏，同一存档生成 3-4 个顾客节点和一个手动节点，包含多物品买卖、移动/旋转。
2. 过去 -> 未来 -> 手动 -> 过去至少恢复 6 次，检查贴图/碰撞、数量、金钱。方便时增加一次非默认议价状态，不以日志零差异替代画面验收。
3. 无需 Verbose，读取 CAPTURE 的 intArrayBlocks/intArraySlots、captureMs/walk 及 RESTORE 阶段、repair、最终校验。必须先确认块实际启用，再比较耗时。
4. 异常停止继续回溯，保留日志并重载。不开游戏、不设提醒，不在本轮实机通过前继续改变载荷或公共扫描。
