# 晨间捕获的摊销成本优化

## 为什么不是“只初始化一次”就能消除每天停顿

最近载入后的晨间节点约 185714 objects / 1017538 slots；普通营业节点约
150000 objects / 830000 slots。首节点旧的 1.3 秒不是相同对象规模的受控对照，
不能直接当作当前存档的基准。最近两次晨间总捕获 2775/3276ms，
其中 access 558/0ms、walk 1576/2672ms；第二次 access 已为零仍很慢，
说明不能只把问题解释成一次性 schema 初始化。

每日晨间锚点必须读取当天新状态，不能直接复用昨天的字段值或对象图。
类型/数组描述和静态字段缓存本已跨节点、跨日保留；没有每天清空/JIT 全部重做。
随后首顾客仍是普通完整捕获，未再执行额外晨间 oracle 或重复预热。

## 改动一：弱身份表清理摊销

旧 ManagedObjects.Id 每当弱身份字典数量是 4096 倍数便扫描整表。
大型冷捕获会反复扫描所有仍活着的对象；删除失效项后，计数取模也可能很快再次命中。

改为每次清理后，至少再分配 max(4096, 清理后表规模) 个新身份才允许下一次整表清理。
重复查找旧身份不会安排清理；只删除已经失效的 WeakReference，不删除活对象，
不更换任何对象 ID。清理仍在原主线程同步运行，无工作线程、无强制 GC。

游戏自带 Mono 的独立局部对照，185714 个对象：

- 首轮旧 400.68ms / 新 136.44ms；复测旧 451.76ms / 新 162.94ms。
- 弱表检查量从 4239360 降至 258048。
- 这只是身份注册局部收益，不是 Unity 完整捕获收益。

## 改动二：删除重复对象索引

StateGraph.Discover 已由 _sources 保证唯一入队，处理序列不必再维护第二个 HashSet。
改用 List 保存已处理顺序和数量，Contains 复用 _sources 的哈希索引。
分区覆盖比较仍检查数量相等及每个对象身份，预算、错误时 processed/discovered
计数、完整遍历与最终 diff 全部保留。

串行 80002 objects / 728000 slots 游戏 Mono 大图对照，optimized=True
四样本捕获中位数旧 215.48ms / 新 213.57ms，**未显著提速**。
保留该项的理由是取消重复索引和哈希维护，不宣传百分比加速。

## 验证与部署

- 游戏 Mono 身份稳定性：强引用存活对象跨 GC/清理的 ID 和反查身份不变；
  重复查询不触发额外 sweep；空身份保持零。
- 完整图/预算/预检/实体块/分区/恢复后 diff/MVID/官方能力扫描均保持。
- 集成测试日志：`out/validation-20261115-morning-errors-tool.log`。
- 两组串行大图日志：`out/morning-perf-serial-{0,1}-20261115.log`。
- 实机 CAPTURE 新增 identitySweepMs/identitySweeps/identityVisited 与三代 GC 次数，
  用于区分首次身份分配、后续普通捕获、弱表清理和 GC 波动。
- 性能改动独立提交，可整体回滚；未跳过每天晨间锚点，不将卡顿延后伪装成消除。
- 尚不能承诺当前存档的晨间或首顾客节点恢复到 1.3 秒；部署后需实机验收。
