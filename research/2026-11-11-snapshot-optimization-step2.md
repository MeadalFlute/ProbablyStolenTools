# 快照优化第二步：数组展开前检查预算

日期：2026-11-11。基于第一步提交 `7687f91`，版本保持 0.8.13，未推送。用户要求每轮改进完成后部署供测试，本轮已部署前两步的合并构建。

## 范围

第一步解决标量校验扩充值表；本步仅解决已知超限数组在拒绝前先分配大量描述数据的问题。

- 新增可选 `IBudgetedStateDescription`；StateGraph 将剩余槽位/逻辑字节预算传给支持该接口的后端。
- Mono 后端先构建元素类型模板，计算数组长度 × 元素跨度及载荷字节。确定无法容纳时，在分配 StateSlot[]、Storage[]、逐元素名字前拒绝。
- 仍由 StateGraph 统一转换成 SnapshotLimitException 并释放半成品。日志保留已捕获计数、上限、队列及来源路径，另带 `array requires slots=..., bytes=... before expansion`。
- 字节需求按引用 IntPtr.Size、标量槽 Size 计算。它仍是逻辑载荷，不冒充常驻内存或分配预算。
- 不支持此接口的后端仍使用原描述路径；普通对象和逐槽检查仍保留。
- 空数组仍可用零槽/零字节预算；多维、非零下界、超长和非法元素类型仍按原规则拒绝。

有效快照仍逐元素保存整个数组，包括集合 Count 外的容量，不裁剪、不改变元素偏移或写屏障，不改变图根、对象身份、恢复顺序或完整校验。多个预算同时不足时，数组预检先报告槽位，不承诺和旧逐槽路径报告同一个首个超限原因。

本步没有处理对象队列的提前预算、描述压缩、恢复前专用普查或分帧，避免扩大单步改动范围。

## 测试

新增五项回归，CheckpointTests 从 80 项增至 **85 项**：

1. 262144 元素 int[]，分别设置极低槽位和字节预算，额外分配小于 1MiB，拒绝后访问器释放、不改数组。
2. 前面对象已消耗部分预算，后续数组按真正的剩余额度拒绝，日志来源指向正确引用。
3. 恰好满足预算的嵌套结构体数组保存全部标量及不同对象引用，修改后逐项恢复。
4. 空数组和各类原先不支持的数组保持既有契约。
5. 后续捕获提前失败不影响已有节点恢复。

完整测试、Release 构建及实际游戏程序集兼容检查均通过：

- Mono Release 0 警告、0 错误。
- 85 项离线测试通过。
- 55 个挂点、73 个私有/快照字段通过。

- 实际 PlayerStore / StoreStation / GameItemElement 数据图、四个数组物品和字典往返通过，六项布局缓存仍排除。

## 分配结果及边界

调查时同类 262144 元素 int[]、maxSlots=1 会先分配约 40.5MiB 再拒绝。本轮最终回归中：

| 失败条件 | 当前线程分配 |
| --- | ---: |
| 槽位预算不足 | 7232 字节 |
| 字节预算不足 | 3624 字节 |

这是 .NET 6 隔离测试，计数不含调用前已创建的数组，包含捕获/异常/释放，不是 Unity Mono 进程内存。

既有 9010 对象/176001 槽合成基准覆盖一致，捕获加完整校验的热读取路径本轮为 79.4ms、102.67MiB。没有同轮旧提交性能对照，不声称正常捕获因此提速；本步主要改善超限失败的分配和响应。
