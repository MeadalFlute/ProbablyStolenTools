# 指定节点跨进程持久化：权限与可行性

日期：2026-11-19。调研范围：不增加当前 manifest 的 `files` 权限，关闭游戏后重新进入同一存档，
允许恢复一个玩家指定节点。本轮没有修改生产代码、版本、配置、部署文件或玩家存档，没有启动游戏或调用 SaveGame/LoadGame。

## 结论

**不是权限上的必然死路，但不能直接序列化当前 Snapshot 就实现。**

| 能力 | 判断 |
| --- | --- |
| 固定保留一份已经存在的原版存档，下次启动继续读取 | 可行，现有文件回退已具备大部分加载基础；不是任意内存节点 |
| 指定节点写成自有纯数据文件，下次重建受支持的游戏状态 | 原理上可行，不要求新增权限；尚未实现恢复原型 |
| 把当前 StateGraph/语义化块落盘后原样 Restore | 不可直接使用，载荷依赖原进程对象身份和活对象 |
| 任意顾客、任意手动时刻、任意第三方 Mod，且保持当前精确恢复保证 | 本轮不能确认可兑现，需要新的跨进程后端和分阶段覆盖证明 |

建议保留当前内存后端，另建**一个固定槽位的持久节点后端**，接受恢复时重新加载场景。
首版优先验证“无当前顾客、无待执行业务的晨间边界”，不是把现有所有闭店/手动节点一概声明可持久化；
之后再推进普通顾客。若必须首版支持任意面板节点，应先做完整图重建可行性闸门，不能先上线近似恢复。

## 权限证据

官方开发指南（2026-11-19 读取 raw 内容）：

https://raw.githubusercontent.com/dragonpan2/probably-stolen-modding/main/ModdingGuide.md

- `files` 覆盖文件读写及 ES3 文件接口；现有包已声明此项。
- 普通纯数据编码不等于加载代码，可以使用固定 DTO / 明确格式的读写器。
- 2026-12-10 起拒绝 `reflection-external`、`dynamic-code`、`native`、`threads`；
  BinaryFormatter/Formatters 反序列化和 Newtonsoft 非 None 的 TypeNameHandling 不能作为捷径。
- 类型名来自文件后再任意实例化，不属于本方案的可接受输入协议。使用编译期已知的类型编号/工厂，
  文件不能指定要执行的程序集、方法或委托。
- 不将调用游戏序列化 API 当作绕过扫描的办法；新后端所有发货 DLL 仍须整体扫描。

## 现有节点不能直接复用的原因

1. `ManagedRuntime.cs:29` 的对象 ID 是进程内弱身份表分配的递增编号，不是可跨进程定位的地址或稳定实体 ID。
   下次启动即使数字相同，也可能对应另一对象。`Get` 依赖原弱引用表。
2. `ManagedStateAccess.cs:702` 把标量值驻留在 `_savedValues`，StateGraph 的八字节 Bytes 是索引令牌，
   不是该字段的可独立解码表示。只写 `_entries` 会同时丢失值表、对象表、类型与存储描述。
3. `SemanticFieldBlock.cs:97` 的 Block 持有原 `_target`、原引用值和 FieldInfo。
   当前“完整实体语义化”指单次遍历的精确字段块，不是独立 DTO / 创建配方 / 持久化实体协议。
4. `CustomerCheckpoint.cs:2093` 的 VisualState 保存 Transform、TreeNodeRender、Sprite 等活引用；
   ShopPhaseVisual、顾客渲染和 tween 状态也依赖当前场景。不能把 InstanceID/对象 ID 写盘后继续使用。
5. `CustomerCheckpoint.cs:1128` 的 store 身份门控有意拒绝更换实例后的恢复。
   删除这条门控不能解决重绑定，只会允许把旧数据写向错误场景。
6. 目前不展开的第三方 opaque 对象仍能依靠本进程原身份存活，跨进程时这个前提不成立。
   它们需要稳定外部引用适配或明确拒绝，不能把这种身份保留宣称为已持久化。

静态布局表解决的是“已存在对象的字段如何合规读写”，没有实现所有对象的安全分配、
Unity 视图重建、委托重建和外部引用定位。扩充生成器可研究，但不能只新增导出文件按钮。

## 原版存档可以复用到哪一步

本次只读反编译输出：
`out/persistent-node-research-20261119/player/PlayerStore.decompiled.cs`、
`items/SaveManager.decompiled.cs`、`scanner/ModScanner.decompiled.cs`。
与 2026-11-10 调研的关键边界一致：

- PlayerStore:161 将 currentClientInstance 排除保存；待执行夜间 Action 等也不属于标准存档载荷。
- PlayerStore:875 的 SaveGame 编码各库存，但没有前柜台 frontInvinvElement。
- PlayerStore:945 的 WriteSlotFile 写 playerStore / storeStation 两个主体。
- SaveManager:51 的 EncodeNode 还会追加全局 savedItemFeatureList；只导出库存 JSON 不够。
- PlayerStore:984 的 LoadGame 会按阶段触发 ModHook、重建库存和执行加载修复，不是无副作用的内存覆盖。
- SaveManager:155 的解码通过物品工厂新建对象，再按局部 uuid 装配关系；uuid 不天然跨不同库存编码作用域唯一。

因此“最新原版存档 + 节点时间戳/顾客 ID”不足以恢复任意节点。
不能仅保存 uniqueId 做引用重绑定：现有测试已覆盖重复/零 uniqueId，需要节点文件自身的唯一 ID 与显式关系表。
不能调用 SaveGame 再拦最后写盘：前面已有库存挂接、运行时间和历史轮转等副作用，违反当前工程约束。
应在自有编码作用域生成标准主体/库存与补充数据，不能覆盖活动槽位。

`SetModData` 适合随原版存档保存少量字符串，但不能保证“固定节点后立刻退出”已经刷入磁盘，
也不能独自承载原生未保存的运行状态。本功能宜用 Mod 专属 sidecar 文件立即保存。

## 推荐路线与另一条路线

### A. 原生数据主体 + 显式运行态扩展（优先）

持久文件至少包括：

- 文件格式/schema、游戏程序集与布局指纹、Mod 版本/相关 Mod 清单；
- runID、slot、节点日期/阶段与展示摘要；不能只凭存档文件名或日期认作同一周目；
- 节点时刻的原生主体与全库存，包括前柜台、特征、方向/容器/共享引用映射；
- 后续阶段支持的当前顾客、剩余队列、预算、议价、已完成对话/交易状态；
- 两套 RNG 的完整状态，而不只是重新设种子；
- 视图/场景角色和资源的稳定定位键，不保存 Unity 句柄。

正常进入同一周目后展示“恢复持久节点”，由玩家确认；重载节点的独立主体、创建业务对象、
接上运行态扩展并重建视图，再校验和开放交互。必要重绑定必须放在相应 onLoaded/ModHook 消费引用之前，
不能假定所有内容都能在 OnGameLoadedLate 后补丁完成。失败不继续开放半恢复状态。

顾客工厂可能随机生成商品或回调，不能直接“按 ID 创建并重播开场”；要保存创建结果与状态，
防止二次生成、二次交易、重复任务/奖励。第三方状态须有适配器，否则拒绝该节点持久化。

**指定已存在的过去节点还有一个额外难点**：SaveManager.EncodeNodes 读取的是当前活对象，
不是节点冻结值。不能在玩家点“固定”时把当前游戏编码成过去节点。初期可在建点时同步生成持久载荷；
若要任选历史节点，则需从已捕获图导出冻结值，或预先为可固定节点保留独立载荷。
不建议临时恢复旧节点→调用原版编码→再恢复当前节点，这会引入真实业务/视图副作用与双重失败窗口。

### B. 可重建的完整类型白名单对象图（研究备选）

理论上可以离线生成已知类型的值编码器、分配工厂与引用修复器；但需解决闭包/委托、无公开构造器、
readonly/集合内部存储、Unity/资源引用、静态单例锚点和 opaque 对象等问题。
不必然需要额外权限，但当前只生成字段读取表并未证明这些能力。不得采用可执行文件输入、
BinaryFormatter、动态 DLL、运行时 IL 或任意类型反射反序列化来补缺。

该路线能否覆盖当前全部节点，必须先做窄原型；不能根据已有静态字段表推断“很容易通用重建”。

## 开发闸门

1. 先对无顾客晨间边界生成独立纯数据文件，退出进程后，进入同周目、不同日仍可确认恢复；
   钱/全部库存/容器/方向/任务/两套 RNG 校验，并验证不污染活动槽位。
2. 再加一个普通顾客样例，验证前柜台、已售/已购物品、预算、回调目标和送客结果，
   不重播到店/开门/奖励；重启前后随机序列一致。未通过不扩大覆盖。
3. 顾客支持范围、选中历史节点导出和第三方状态分别设验收闸门，不以首个样例通过宣传任意节点。
4. 文件头先验证周目/槽位/版本/Mod 组合；解析有大小/数量/深度上限，未知类型编号拒绝，
   不从输入加载程序集或执行方法。严格版本拒绝意味着稳定版与 beta 不默认互读持久节点。
5. 单固定槽位用临时文件 + 原子替换，失败保留上一份；独立于普通节点 LRU，不能睡觉/清内存节点时删除。
   自动隔离损坏文件、提供删除/原因提示；恢复先保留原存档恢复路径。
6. 新发货 DLL 官方扫描仍仅 files；离线往返、独立进程往返和 Unity 实机分别通过。

**最终判断：可以立项为新后端；不需要先申请新权限，但完整任意节点支持仍属条件性可行，
不能当作已完成或只需磁盘序列化的小改动。只保存一个节点降低存储/UI成本，不降低重建正确性的要求。**
