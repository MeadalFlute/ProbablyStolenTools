# 当前快照流程与原版保存流程对照

日期：2026-11-10。基线：`c243a96`，正式版 0.8.13。

本轮仅检查源码、读取原版反编译结果和运行隔离的托管实验。不修改运行代码、不部署、不启动游戏、不调用原版保存/加载、不读写玩家存档。原版程序集 SHA256 重新确认仍为 `725CB999D019DFF1FF31BED353C7F9BB8D81A7605A15DE1F80F5A3A6CF7B1D05`。

## 结论

**有明确优化空间，优先做校验无副作用、描述数据减重与提前预算检查；其次减少恢复前的重复完整捕获。** 不建议第一步就分帧，也不建议直接换成原版 SaveGame/LoadGame。

原版最值得借鉴的是语义化保存：记录物品状态、形状、特征和库存链接，而非保存集合内部布局、所有回调与缓存。完整替换的可行性和运行态缺口见 [原生存档替代调研](2026-11-10-native-save-rewind.md)。本报告关注保留现有即时回溯时还能改进什么。

## 1. 两条流程的差异

| 环节 | 现有快照 | 原版保存/加载 |
| --- | --- | --- |
| 入口 | PlayerStore / StoreStation / EmporiumEntry 全字段根，其他管理器选定字段及 RNG | PlayerStore.SaveGame 刷新各库存 JSON，再写 PlayerStore / StoreStation |
| 库存 | 遍历物品、库存、标签、集合内部数组、委托目标等业务对象图 | SaveManager.EncodeNodes 按物品生成 SaveItemNode，记录子库存链接 |
| 标签 | 保留字典身份、桶、条目数组和状态对象 | 克隆 state；序列化时只输出有有效内容的标签键值 |
| 派生状态 | 同时保留运行中的派生字段和必要回调 | 不逐字段保存全部运行缓存；解码、工厂和加载逻辑重新生成 |
| 物品身份 | 保留原对象并原地还原 | DirectoryMaster 工厂重新建物品，再装配库存 |
| 显示 | 单独保留 VisualState，按既定顺序恢复几何 | 新建/装配对象时建立显示 |
| 营业运行态 | 顾客、队列、对话、议价、前柜台、随机源等 | 多项明确不序列化，前柜台不在 SaveGame 编码清单 |

原版不是没有成本：编码克隆标签和形状、生成节点和 JSON；EncodeSaveItem 还临时挂接窗口，EncodeNode 追加全局特征列表。不能把这些方法当作只读、线程安全的后台任务。

## 2. 目前捕获与恢复的工作量

捕获（`CustomerCheckpoint.cs:532`）：

1. 建立访问器和根，完整 BFS 捕获。
2. 扫描图中对象，保存物品、窗口、视觉和随机状态。
3. 完整 Differences 校验。
4. 几何诊断、历史入列/淘汰、重建保活物品集合、日志。

恢复（`CustomerCheckpoint.cs:768` 起）：

1. 验证目标视觉对象，再完整捕获当前业务图。
2. 完整读取目标图进行预检；返回的差异列表未使用，但读取失败仍会阻止写入。
3. 从当前图寻找目标之外的物品和窗口。
4. 还原业务图、刷新视图及原生 Validate。
5. 完整校验；刷新改动了业务图时第二次还原。
6. 恢复视觉、修复几何、恢复最终变换，再完整校验。
7. 成功后才清理废弃时间线视图。

完整校验不是只看前 12 个槽：12 只是差异消息数上限，实际仍读全图。不能用提前返回或减少校验次数来伪装性能改善。

## 3. 可优先处理的具体问题

### A. 差异校验会扩充被检查快照的值表

位置：`ManagedStateAccess.cs:312`、`StateGraph.cs:120`。

ReadValue 既用于捕获，也用于 Differences。遇到未见过的标量时，会向该访问器的 `_values` / `_savedValues` 添加令牌和值。恢复前读取变化后的局面、或视图刷新后的校验，都可能把不属于节点的数据留在旧节点里，直至节点释放。ByteCount 不反映这些增长。

隔离复现：仅一个 int 字段，捕获后改变成 1000 个不同值，每次完整 Differences。值表从 **1 项变成 1001 项**，图 ByteCount 始终为 **8**；原值恢复仍通过。这是无必要的保留，不是已经证明的玩家内存泄漏主因。

建议：分离“捕获/登记值”和“只读比较值”。例如为访问器提供显式比较操作，校验直接和原令牌对应的值比较，不登记新令牌；其他后端保持原有字节比较语义。浮点必须保留位模式比较，覆盖正负零、NaN、double、枚举和可空类型，不能简单换成普通 Equals。

这是较低风险的首项实现候选：不改变图覆盖、身份、恢复顺序或完整校验范围。

### B. 超限检查发生在数组描述分配之后

位置：`ManagedStateAccess.cs:117`、`StateGraph.cs:65`。

Describe 一次构建整个数组的 StateSlot[]、Storage[] 和逐元素名字，随后 StateGraph 才逐槽检查预算。

隔离复现：262144 元素的 int[]，maxSlots=1，仍先分配 **42,446,016 字节（约 40.5 MiB）**，随后才抛出 slot limit；本次约 48.6ms。数字是 .NET 6 当前线程分配，不是 Unity Mono 常驻内存。

建议：描述阶段先用数组长度 × 元素跨度计算所需槽位，和剩余预算核对；或采用有预算的惰性槽迭代。对象上限也应考虑已发现、待处理对象，避免超限前持续扩大 pending/source 表。必须保留可定位的来源路径和半成品释放。

### C. 槽位描述及标量令牌远大于日志中的 bytes

位置：`ManagedStateAccess.cs:23`、`:117`、`:312`，`StateGraph.cs:31`、`:76`。

当前每槽 bytes 是 8 字节令牌/引用计数，不是完整内存预算。它没有包含 Entry 容量、Storage、字段名、来源索引、值表、保留字符串、视觉状态和被保活的 Unity 对象。

默认 MaxSlots=3000000，每槽至多 8 字节，逻辑 ByteCount 至多约 **22.9 MiB**，因此默认 MaxBytesMB=256 并不能有效约束这类快照的实际内存。

另一隔离样本：10000 个不同 int 的数组，逻辑 bytes=80000，捕获加完整校验的当前线程分配为 **5,784,816 字节**。分配量包含临时对象，不能直接当作节点保留内存，亦不能乘 20 得出历史常驻量。

建议分两步：

- 共享有界、不可变的类型字段模板；当前 `_schemas` / `_elementSchemas` 每节点重建，只有字段读取器跨节点缓存。选定根字段集合必须进入缓存键，不能污染完整类型模板。
- 数组保存元素模板和索引，不为每个元素复制完整描述与字符串；诊断时再生成名字。Entry/值令牌可进一步紧凑化。

共享内容不能带实例、根、数组下标或可变值；保持 `i * stride + j` 和原数组写屏障规则。历史总内存预算应与磁盘检查点容量分开设计，不能直接复用逻辑 ByteCount 宣称限制了进程内存。

### D. 回溯前完整捕获当前图，但不用于回滚

位置：`CustomerCheckpoint.cs:778` 至 `:799`、`:908`。

current 只使用 Objects 枚举新增物品/窗口，最后 Dispose。没有 current.Restore；写入后失败仍要求重新加载。因此这份完整标量快照增加耗时、峰值分配，也可能因当前图槽位超限而阻止恢复一个本来有效的旧节点。

建议：实现专用“只读对象普查 + 预检”模式，遍历同样的引用覆盖，保留身份、必要字段可读性和错误检查，但不保存不用的标量令牌/Entry。目标预检的完整读取也应无副作用。

这比 A 风险高：不能只遍历可见库存，否则闭包、嵌套物品、已售对象或窗口可能遗漏；不能直接删掉现有 Capture 和 Differences，丢失写入前安全检查。

### E. 更完整但低频的测量

现有 total 包含历史淘汰/保活重建，未单列；TraceBargain 位于计时日志之后。恢复没有分阶段耗时。

建议每次节点仅输出一条摘要，包含 walk/visual/verify/history/cleanup、恢复 preflight/write/refresh/finalVerify，及类型/来源聚合。对象类型、数组长度、容量/有效条目和估算描述大小可在详细诊断模式下按类别汇总，而不是逐对象刷日志。分配指标必须确认游戏 Mono 可用且不影响正常运行。

首先量出各类对象/集合的成本，再决定是否隔离 PlayerStore.saveBags、savedItemFeatureList、旧库存 JSON 等原生保存缓存。它们目前随完整根进入图；不能仅凭名字直接排除，也不能通过调用 SaveGame 来刷新或清理。

## 4. 借鉴原版的较大改造

最大的结构性收益方向是：**物品/标签/库存语义记录 + 原对象原地恢复 + 必要运行态图**。

- 借鉴 SaveItemNode 保存状态、形状、特征与链接；在稳定边界重建可确定的派生数据。
- 不直接调用 DecodeNodes 替换物品，否则旧顾客闭包、议价和检查窗口仍可能引用旧对象。
- 当前原样恢复字典依赖容量、桶、空槽和内部版本；不能只保存 Count 个数组元素，不能直接过滤“空标签”或删除 modifiedState 后宣称兼容。
- 即使缩小根，委托/闭包也可能重新走回完整库存；需要显式边界和独立语义校验。
- 必须继续解决前柜台、跨顾客、拆分合并、已销毁物品保活、第三方模组不透明对象的覆盖问题。

这是独立后端/集合适配器工程，不能和保守数据结构优化混成一笔修改，也不能在没有同存档实测前承诺收益。

## 5. 分帧与触发频率

目前仍是稳定门控后的同步捕获，不启用跨帧。

分帧读图可能混合不同时间点；timeScale=0 不会停止所有 UI、unscaled 回调或其他 mod 写入。最终 Differences 能发现部分变化，但不能把撕裂读取变成一致节点。需要真正的冻结协议或版本化/重试方案，并限制主线程每帧预算。

若后续采用，遵照用户要求独立 Git commit，可单独回退。不要在此之前把任务切成每帧 2ms 就认为问题解决。

把自动节点改为仅开门、关门和成交后，也会改变“回到该顾客交互前”的功能含义；不应作为透明优化直接套用。先保留现有节点语义。

## 6. 推荐顺序与验证

1. 先分离校验比较与值登记；以当前后端为对照，验证值表不因校验增长。
2. 提前检查数组/队列预算，压缩描述元数据；保持同根的对象、槽、值、引用和来源覆盖一致。
3. 补充少量阶段/类型汇总诊断，在相同游戏状态交替比较。
4. 实现恢复专用普查/预检，独立验证新增物品/窗口清理和写入前失败边界。
5. 只有上述收益不足，再考虑语义化物品后端；分帧另案处理。

每步需运行快照回归与实际程序集兼容检查。游戏验收必须包括售出、移动、旋转、前柜台、容器嵌套、拆分合并、跨顾客、重复回溯、未来节点往返及新分支淘汰；不能只断言 diff=0。

不变约束：完整捕获校验、保留对象身份、原生布局缓存排除、VisualState → 几何修复 → 最终变换 → 完整校验的顺序、不重放交易/到店业务、不修改原生存档或索引。
